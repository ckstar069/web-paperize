### 1.2 三条获取路线对比

| 维度 | A：网络捕获 | **B：endpoint 直取（推荐）** | C：DOM 反向滚动 |
| --- | --- | --- | --- |
| 完整性 | ✅ 服务器响应，含全部分支 | ✅ 同一数据（`/backend-api/conversation/{id}` 即页面数据源） | ⚠️ 依赖虚拟化器逐段 hydration，长会话耗时且可能不完整 |
| 刷新页面 | **必须**（`Page.reload ignoreCache`） | **不需要** | 不需要 |
| 私有接口敏感度 | 低（只按内容特征 `mapping+current_node` 识别，不依赖 URL 模式） | 高（依赖 `/api/auth/session` 与 conversation endpoint 形状） | 低（DOM）但 UI 改版即碎 |
| 登录态 | 页面自己请求，零处理 | 页面同源 fetch 自带 cookie；token 仅内存中使用 | 同 A |
| MAIN world | 不需要 | **不需要**（Cocoanetics 以默认 ISOLATED world 实证） | 不需要 |
| host permission | 无（debugger） | **未证实**：Cocoanetics 自己声明了 chatgpt.com host_permissions，不能作为"无需"的实证；本项目仅凭 activeTab 是否足够 → §8 实验项 | 无 |
| 失败检测 | 弱（45s 超时 + 响应嗅探） | **强（HTTP 状态码即失败信号）** | 弱（无完成判据） |
| 副作用 | 刷新破坏用户现场（滚动位置/未发送输入） | 无 | 滚动后需恢复 |
| 许可证 | MIT | MIT（两个独立实现互证） | maks-bond 无 LICENSE |

**结论（2026-09-10 规划审核后定稿）：B 为主路线；B 失败时显式提示"完整会话获取失败"，由用户自行选择是否改用普通整页导出，不做任何静默/自动 fallback；C 移入 backlog，仅当 B 被 endpoint 改版实际打断后再考虑实现；A 不采纳。** 三个 MIT 项目对 B 路线独立实现互证，稳定性可信。

### 1.3 会话数据的关键事实（materialize 必须处理）

来自 Cocoanetics/pionxzh 的实现（这些是"完整数据"里仍然存在的坑）：

1. **活动分支**：`mapping` 是树（含重新生成的废分支）；正确路径 = `current_node → parent → … → root` 反转。
2. **可见性过滤**：跳过 `metadata.is_visually_hidden_from_conversation / is_hidden / hidden / is_redacted`。
3. **引用两代格式**：旧式 `【4†(来源)】` + 新式私有码位分隔符 `U+E200…U+E201`。
4. **旋转混淆键**：`{{file:…}}` 占位符的文件名藏在 metadata 里**键名会轮换**（如 `n7jupd_crefs`）——必须按值形状扫描，不能按键名。
5. **Canvas 文档**：内容在 `canmore.create_textdoc`（全文）与 `canmore.update_textdoc`（正则补丁）的工具消息里，需回放补丁重建。
6. **图片/附件**：`image_asset_pointer`（`sediment://`/`file-service://` 指针，需带 Bearer 换取下载 URL）、代码解释器 `sandbox:` 路径。
7. **特殊会话**（pionxzh）：分享页（`__share__` 前缀）、临时会话（id 不在 URL，靠 `/backend-api/f/conversation` 流识别）、项目/gizmo 会话。
8. **LaTeX**：正文含 `$$…$$`/`\[…\]`，处理 markdown 时需占位符保护（pionxzh 的 `╬n╬` 方案）。
9. **ChatGPT 滚动根是 `[data-scroll-root]` 内层容器，不是 window**（maks-bond）——C 兜底与通用 prepare 都要知道。

### 1.4 materialize 设计（本项目的新增工作，无人做过 PDF 版）

```
conversation JSON（不可信输入）
  → 过滤 + 活动分支重建（§1.3-1/2）
  → 消息渲染管线（§1.3-3/4/5/6/8）
  → safe RenderModel（安全契约见下）
  → DOM builder
  → 注入当前页（Shadow DOM 隔离 ChatGPT 全局 CSS）
  → 走现有 capture pipeline（screen media + printToPDF）
  → restore（现有 undo log 机制）
```

**安全契约（硬红线，2026-09-10 审核新增）**：conversation JSON 必须视作不可信输入（用户消息、搜索内容、代码块、附件名都可能是任意字符串）。禁止未经 sanitizer 的 `innerHTML`；正文/代码一律 `createElement + textContent`；URL 做 scheme/来源 allowlist（http/https），`javascript:` 与事件处理器 HTML 不得进入 printable DOM；消息中的 HTML 片段默认按文本呈现。

**生命周期（审核新增）**：undo store 初始化从 `primePage()` 独立为 `beginCaptureState()`，使 adapter 可在 materialize 前建立稳定 undo owner：

```
ChatGPT:  beginCaptureState → adapter.acquire → adapter.materialize → settle → measure/print → restorePage
普通网页: beginCaptureState → primePage → declutter → expand → print（行为不变）
```

materialized 文档是自生成的干净 DOM，**不再执行**通用 primePage/declutter；printable root 用 Shadow DOM（或等效 scoped/reset 样式）与 ChatGPT 全局 CSS 隔离。

**实现顺序（内部两步，不设正式子版本号）**：第一步做普通会话的核心质量（活动分支、user/assistant、markdown 标题/列表/代码块/表格/普通链接）；跑通 100+ 消息会话后，再逐个加入 citations、images/files、Canvas、sandbox、share、临时会话。LaTeX 保持原样文本。

失败时（endpoint 401/404、无消息）显式报错"完整会话获取失败"，由用户选择是否改用普通 V0.1 导出（见 §1.2，不自动 fallback）。

### 1.5 隐私表述修订（硬要求，2026-09-10 审核定稿文案）

路线 B 是向 ChatGPT/OpenAI 服务发起请求（含后续图片/附件可能的 CDN endpoint），不能再宣称"扩展完全不产生网络请求"。最终文案：

> **No web-paperize server, no telemetry. Conversation data is requested only from ChatGPT/OpenAI services needed to retrieve the chat and its assets. Nothing is sent to a web-paperize service or unrelated third party.**

README/popup 文案在 P2 批次落地时同步修改。

### 1.6 site-adapter 边界（架构原则）

```
src/adapter/
├── index.js          # getAdapter(url)：按 canHandle 选择，普通网页返回 null
└── chatgpt/
    ├── detect.js     # canHandle(url)：chatgpt.com(/c/<uuid>|/g/<gizmo>/c/<uuid>)
    ├── acquire.js    # 注入页面的取数函数（ISOLATED world，自包含，同 prepare.js 约束）
    └── materialize.js# conversation JSON → 可打印 DOM 模板
```

- service-worker 在 `capture` 前查询 adapter；`acquire()` 失败 → **显式报错"完整会话获取失败"，不自动生成可能不完整的普通页面 PDF**，由用户自行选择是否改用普通导出（与 §1.2 定稿一致）。
- **通用 `prepare.js` 不出现任何 ChatGPT 特例**；不为 Claude/Gemini 预留框架，只保证第二站点接入时新增目录即可。

## 2. V0.2 通用功能（第一批实现）

### 2.1 Element / Selection 导出

### 2.2 单张连续长页
- 测量法：`paperHeight = contentHeight×scale/96 + 2×margin`（V0.1 定点迭代已保证宽度测量正确）。
- **独立分页 CSS（审核要求，V0.2.0 开发前必须实现）**：单页模式不沿用 V0.1 的分页友好规则——`avoidBreaks` 强制关闭，并注入 `break-before/after/inside、page-break-*` 重置为 auto（screen-to-pdf 已验证的思路），否则 paperHeight 算对仍可能被 CSS 强制分出第 2 页。
- **高度上限（实验事实与推测分离，审核要求）**：
  - 实验事实（Chrome 152.0.7977.83 headless CDP printToPDF）：≤910in 单页成功；≥915in 显式报错 `Printing failed`；失败边界位于 910–915in 之间。上游 200/800/1000in 三个数字与实测不符。
  - 推测（未证实）：边界对应 65536pt（2^16）PDF 后端数值边界——仅作假设记录，不写作事实。
  - **900in 仅为 renderer candidate limit；product-safe cap 定为 200in**（兼容性实验已完成，见 `docs/benchmark/2026-09-10-height-limit.md`：Chrome 输出无 `/UserUnit`，>200in 即超出 PDF 默认 user space 建议 14400pt；macOS 全栈与 Chrome PDFium 实测可渲染 900in，但 Windows 阅读器未验证）。实现取 `MAX_CONTINUOUS_INCHES = 200`：超过或 printToPDF 报错 → 自动回退 A4 分页并提示；后续补验后再提高。
  - 实验驱动脚本入库 `tests/tools/height-experiment/`，结果记录于 `docs/benchmark/2026-09-10-height-limit.md`，可复现。
- 完成判据：300in/900in（或降档后的产品上限）/超限三档测试页各导出一次，前两档单页完整可读、超限档自动分页；大尺寸档在 Chrome Viewer 与 Preview 中正常打开。

## 3. Snapshot 双引擎（本轮只定接口，不实现）

## 5. 对 V0.1 的修改边界

允许改动：`capture.js`（入口分派 adapter/scope/单页）、`service-worker.js`（消息路由）、`settings.js`（新字段）、popup UI。**不改动**：`cdp.js`、`prepare.js` 既有函数语义（只允许新增函数）、`download.js`、manifest 既有权限语义（新增 `contextMenus` 需评审确认）。出现 regression 时以最小修复为原则并记录。
